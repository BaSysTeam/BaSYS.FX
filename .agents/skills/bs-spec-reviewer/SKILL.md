# BaSYS.FX Spec Reviewer

Проверять постановку OpenSpec до реализации или при уточнении плана. Codex:
`$bs-spec-reviewer`; Cursor: `/bs-spec-reviewer`. Отчёт писать на английском;
комментарии в цитируемом коде сохранять на английском.

BaSYS.FX — публичный open-source проект. Заголовки, находки, рекомендации,
вердикт и таблицы отчёта писать на английском независимо от языка запроса
и исходных OpenSpec-артефактов. Цитаты из источников можно сохранять в оригинале
с пояснением на английском. Ответ пользователю может быть на языке разговора.

## Границы работы и контекст

- Не менять код, тесты, спецификации, proposal, design, tasks, `.openspec.yaml`,
  статусы и чекбоксы. Единственный постоянный результат — новый отчёт.
- Рабочий каталог команд — корень BaSYS.FX; OpenSpec расположен в `openspec/`.
  Прочитать `openspec/config.yaml` и `.openspec.yaml` выбранного change.
  Сейчас применяется `spec-driven`: текст артефактов, структурные
  заголовки OpenSpec и SHALL/MUST — английские. Это правило относится к исходным
  артефактам планирования, а не к языку review-отчёта. Фактическую схему и обязательность
  артефактов уточнять через status/instructions.
- Здесь нет обязательной схемы `basys-detailed`, скрипта
  `scripts/check-openspec-tasks.mjs`, `CONTEXT.md` и каталога заданий этапов.
  Не требовать их и не создавать. Нормальный план — один `tasks.md` с разделами
  и нумерованными чекбоксами. Файлы этапов проверять, только если они существуют
  или прямо предусмотрены выбранным change.
- Не выполнять apply, archive, sync, new change, update, установку зависимостей,
  сборку или публикацию. Связанные задачи других репозиториев читать по ссылкам
  при наличии доступа; не редактировать и не закрывать их.

## Выбор объёма

| Запрос | Что проверять |
| --- | --- |
| Имя change | Все существующие артефакты и связанные задачи |
| Конкретный proposal/design/spec/tasks | Названные артефакты и согласованность с остальным пакетом |
| Раздел, этап или файл задачи | Этот объём, относящиеся требования и зависимости |

Если change не назван, использовать однозначный контекст. Иначе выполнить
`openspec list --json`; если выбор остаётся неоднозначным, уточнить его.
Для незавершённого планирования оценивать существующий материал: отсутствие
артефакта — находка только при требовании готовности и обязательности по схеме.
Не считать пропущенный по схеме артефакт отсутствующим.

## Ход ревью

1. Зафиксировать объём и состояние кода: `git rev-parse HEAD`, `git status --short`.
   Незакоммиченные изменения и новые файлы учитывать отдельно от HEAD.
2. Из корня выполнить доступные проверки:

   ```powershell
   openspec status --change "<change>" --json
   openspec validate "<change>" --strict
   ```

   При необходимости получить правила артефакта:
   `openspec instructions <artifact-id> --change "<change>" --json`.
   Записать результат каждой проверки. Если CLI недоступен, продолжить ручное
   ревью и отметить ограничение; не устанавливать CLI автоматически. Ошибка
   валидации содержимого — находка, сбой окружения — ограничение проверки.
3. Прочитать proposal → delta specs → design при наличии → tasks. Для изменяемых
   требований сравнить полный блок с `openspec/specs/<capability>/spec.md`.
   Пока каталог основных specs пуст, это не дефект само по себе; новые capability
   допустимы. Для MODIFIED/REMOVED/RENAMED должна существовать проверяемая основа.
4. Проверить утверждения о текущем коде через чтение и поиск:
   `src/index.ts`, `src/common.ts`, `src/dateExtensions.ts`, `src/table/`,
   `src/query/`, `tests/`, `README.md`, `docs/`, конфигурации пакета и сборки.
   Имена, сигнатуры, типы, экспорты и существующие тесты подтверждать фактически.
   Обещанное новое API не путать с утверждением, что оно уже реализовано.
5. Если пакет ссылается на внешнюю исходную задачу, прочитать релевантный контракт
   при наличии доступа. Отделять библиотечные обязательства от работ сервера,
   фронтенда и выпуска. Недоступный источник отметить; не выдавать предположение
   о нём за проверенный факт.
6. Проверить пункты ниже, построить трассировку требований и сохранить отчёт.
   В ответе дать вердикт, главные находки и ссылку. Исправление артефактов —
   отдельный запрос; для него доступен `openspec-update-change`.

## Проверки постановки

- **Согласованность:** proposal, specs, design и задачи описывают один контракт;
  каждое требование имеет сценарий с проверяемым WHEN/THEN, задачи и проверку
  результата. Технические детали обоснованы в design, внешнее поведение — в specs.
  Учитывать намеренную совместимую эволюцию и явно согласованные breaking changes.
- **Delta specs:** корректно выбраны ADDED/MODIFIED/REMOVED/RENAMED; MODIFIED
  сохраняет неизменённую часть исходного требования. Названия capability и
  ссылки совпадают. Не требовать старую spec для действительно новой capability.
- **Публичный API:** описаны сигнатуры, возвращаемые значения, defaults, допустимые
  входы и ошибки, экспорт через `src/index.ts`, влияние на декларации, примеры
  и обратную совместимость. Для библиотечного API допустимы технические имена.
- **Числа, даты, таблицы:** там, где это относится к изменению, заданы правила
  округления и IEEE 754, локальное время/UTC, точность сериализации, мутация
  входов, пустые значения, порядок и дубликаты строк, ключи и итоги операций.
  Не требовать все эти сценарии от изменения, которое их не затрагивает.
- **Модели запросов:** определены JSON-поля, enum и обработка
  `null`/`undefined`/`false`/`0`, порядок fluent-операций, ошибки до мутации;
  сохранён контракт провайдера. Не приписывать библиотеке серверную фильтрацию,
  SQL и добавление контекста формы. При межрепозиторном изменении явно описаны
  совместимость и порядок поставки зависимых компонентов.
- **Среды и сборка:** решение согласуется с `tsconfig.json` и Rollup: текущие
  target ES6 и lib ES2017/DOM, ESM/UMD/IIFE `BaSYSFX`, декларации. Для нового
  runtime API обоснована доступность в поддерживаемых средах; не предполагать,
  что TypeScript автоматически даёт полифиллы.
- **Задачи и зависимости:** нумерация однозначна, требования покрыты конкретными
  задачами и критериями готовности, порядок выполним без циклов. Этап может
  исполняться по указанному контексту. Не навязывать файлы этапов и отдельные
  заголовки Blocked by обычному плоскому `tasks.md`.
- **Проверка результата:** предусмотрены релевантные Jest-тесты в `tests/`,
  публичный импорт и ошибки; при необходимости — `npm test`, strict TypeScript,
  `npm run build` и проверка бандлов/деклараций. Контрактные ожидания заданы
  независимо от алгоритма. Не считать ts-jest с `strict: false` полной проверкой типов.
- **Поставка:** если меняется версия, согласованы `package.json` и версия самого
  пакета в `package-lock.json`; не требуется менять версии зависимостей.
  Публикацию и обновление внешних задач не добавлять в план без основания.
  Если план их уже требует, проверить критерии, зависимости и границы полномочий.

## Severity и вердикт

- **Critical:** противоречие контракта, невыполнимая зависимость или ложная
  предпосылка, блокирующая корректную реализацию.
- **High:** существенный пропуск сценария, несовместимость API/JSON/среды,
  непроверяемое требование или нерешённый вопрос, меняющий реализацию.
- **Medium:** частичная трассировка, неясный критерий приёмки или декомпозиция,
  повышающая риск пропуска; неподтверждённое решение или риск без меры снижения.
- **Low:** неработающая ссылка, терминология или оформление с конкретным эффектом.

Оценивать последствия, а не автоматически назначать severity по названию раздела.
Вердикт: `Ready for implementation`, `Ready after corrections` или `Requires rework`;
для промежуточного планирования явно ограничить вывод проверенной частью.

## Отчёт

Для одного активного change создать
`openspec/changes/<change>/reviews/YYYY-MM-DD-HHmm-<topic>-spec-review.md`.
Для архивного или нескольких changes —
`review/YYYY-MM-DD-HHmm-<topic>-spec-review.md`.
Время — Europe/Moscow, topic — kebab-case, для этапа добавить `stage-N`
(например, `stage-2-1`). При совпадении имени добавить числовой суффикс;
старые отчёты не перезаписывать и не перемещать.

Из change/reviews ссылки на артефакты — `../proposal.md`, `../tasks.md`,
`../specs/<capability>/spec.md`; на код — `../../../../src/`, тесты —
`../../../../tests/`, основные specs — `../../../specs/`.
Для `review/` вычислять пути от него: `../openspec/`, `../src/`.

```markdown
# Spec Review — <topic>

**Date:** YYYY-MM-DD HH:mm (Europe/Moscow)
**Change and scope:** <name, artifacts/stage>
**BaSYS.FX revision:** <HEAD and working tree state>
**Reviewed sources:** <links to artifacts and external contracts if applicable>

## Verdict
**Readiness:** <verdict and supporting reasons>

## Automated checks
| Check | Result |
| --- | --- |
| OpenSpec status | <result or reason for skipping> |
| OpenSpec validate --strict | <result or reason for skipping> |

## Findings
### 1. <title> [High]
- **Location:** <link, section/task>
- **Issue:** <implementation risk>
- **Evidence:** <artifact quotation, code link and lines>
- **Recommendation:** <what to clarify/correct without rewriting artifacts>

## Requirements traceability
| Requirement / Scenario | Tasks | Test / validation | Status |
| --- | --- | --- | --- |
| <capability: requirement> | <1.1, 1.2> | <scenario and expected result> | <covered / partial / missing> |

## Ranked findings
| Done | # | Severity | Finding | Artifact |
| --- | --- | --- | --- | --- |
| [ ] | 1 | High | <title> | <link> |

## Review limitations
<Unavailable sources, environment limitations and incomplete planning.>
```

Для одного этапа трассировать только относящиеся к нему требования. Все находки
перенести в итоговую таблицу по убыванию severity с пустыми `[ ]`. Если находок
нет, явно написать об этом и оставить строку `No findings` без чекбокса.
