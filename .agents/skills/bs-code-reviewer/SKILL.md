# BaSYS.FX Code Reviewer

Проверять реализацию библиотеки `@basysteam/basys-fx`. Результат — отчёт на английском;
комментарии в цитируемом коде сохранять на английском. Codex: `$bs-code-reviewer`;
Cursor: `/bs-code-reviewer`.

BaSYS.FX — публичный open-source проект. Заголовки, находки, рекомендации,
выводы и таблицы отчёта писать на английском независимо от языка запроса
и исходных OpenSpec-артефактов. Цитаты из источников можно сохранять в оригинале
с пояснением на английском. Ответ пользователю может быть на языке разговора.

## Границы работы

- Не изменять код, тесты, документацию, версии, lock-файл, артефакты OpenSpec
  и отметки задач. Единственный постоянный результат — новый файл отчёта.
- Проверять заданные файлы, diff, ревизию или реализацию указанного change.
  Связанные модули и тесты читать для проверки выводов. Не требовать выбора
  frontend/backend: это самостоятельная библиотека TypeScript.
- Если объём не задан, использовать контекст запроса и `git status --short`,
  `git diff`, `git diff --cached`; читать относящиеся к задаче untracked-файлы.
  Если контекст не позволяет выбрать объём, уточнить его.
- Не устанавливать зависимости, не публиковать npm-пакет, не менять соседние
  репозитории. Ссылки на внешние задачи дают контекст, но не право их закрывать.

## Карта проекта

Все пути ниже относительны корню BaSYS.FX. Перед ревью сверить их с рабочей копией.

| Область | Источники и особенности |
| --- | --- |
| Публичный API | `src/index.ts`: реэкспорты и побочный импорт `dateExtensions` |
| Общие функции | `src/common.ts`: числа, условия, создание/разбор таблиц, форматирование, `from` |
| Даты | `src/dateExtensions.ts`: расширение `Date.prototype`, локальные и UTC-методы |
| Таблицы | `src/table/`: `DataTable`, колонки, join/group/union/distribution |
| Запросы | `src/query/`: построитель, сериализуемые модели, фильтры, параметры, границы |
| Провайдер | `src/query/queriesProvider.ts`: `IQueriesProvider`, внешние `globalThis.QueriesProvider` и `DB_NAME` |
| Тесты | `tests/*.spec.ts`, Jest + ts-jest; настройки в `jest.config.js` |
| Сборка | `tsconfig.json`, `rollup.config.mjs`, `package.json`: strict TypeScript, target ES6, lib ES2017/DOM; ESM, UMD, IIFE `BaSYSFX`, декларации |
| Контракт и примеры | `README.md`, `docs/`, выбранный change в `openspec/changes/` |

## Проверки

Выбирать применимые проверки; замечание должно иметь подтверждённый сценарий
и последствие. Существующие `any`, объявления `function` или стиль соседнего
приложения сами по себе не являются дефектом библиотеки.

- **API и совместимость:** экспорт через `src/index.ts`, соответствие сигнатуры
  runtime-поведению и декларациям; значения по умолчанию, исключения, сохранение
  прежнего контракта вне согласованных изменений. Проверить доступность новых
  возможностей через публичную точку входа, а не только прямой импорт файла.
- **Среды выполнения:** не появляется ли обязательная зависимость от DOM, Node,
  локали или недоступного API. `lib` в TypeScript не гарантирует наличие API
  в среде потребителя. Проверять подключение ESM/UMD/IIFE по затронутой области.
- **Даты:** локальное время и UTC, переходы суток/месяцев/лет, високосные даты,
  DST для локальной арифметики, невалидные даты, мутация исходного `Date`,
  согласованность расширений прототипа с типами. Для API, принимающего даты из
  другого JS-контекста, проверить cross-realm Date и отсутствие чужих расширений.
- **Числа и форматирование:** ноль и `-0`, отрицательные значения, половины,
  IEEE 754, точность, `NaN` и бесконечности, диапазоны параметров, разделители
  и форматные токены. Отличать числовое округление от строкового форматирования;
  ожидаемое поведение брать из контракта, не из предпочтений ревьюера.
- **Таблицы:** пустые наборы, отсутствующие/повторные колонки, типы значений,
  null, ключи соединения и группировки, дубликаты и порядок строк, суммы и
  распределение остатков, сериализация/восстановление. Проверять неожиданные
  мутации и разделяемые ссылки; сложность оценивать на конкретном объёме данных.
- **Запросы:** fluent-цепочки и порядок операций; JSON, значения enum, имена
  полей, различие `null`/`undefined`/`false`/`0`, восстановление классов из модели;
  сохранение `where`, `parameters`, `filters` при добавлении границ. Для границ
  сверять локальную сериализацию до секунды, правила `column`/`excludeOwn`,
  проверку ошибок до изменения модели с действующим контрактом. Библиотека
  передаёт модель провайдеру; серверные SQL-условия и значения по умолчанию
  нельзя считать реализованными здесь.
- **Внешнее состояние:** отсутствие провайдера, отклонение Promise, изоляция
  `globalThis` и прототипов между тестами. Не требовать настоящую БД для unit-тестов.

## Ход ревью и проверка тестов

1. Прочитать запрос, действующие инструкции, `package.json`, конфигурации и
   относящиеся к реализации требования. Зафиксировать `git rev-parse HEAD`
   и наличие изменений рабочей копии: HEAD не описывает незакоммиченный код.
2. Проследить поведение от публичного API через реализацию до провайдера или
   результата; сопоставить его со спецификацией и вызывающими местами в репозитории.
   Внешний код проверять только при наличии ссылки и доступа; иначе указать ограничение.
3. Найти связанные тесты самостоятельно. Отдельно оценить успешные сценарии,
   границы, ошибки, отсутствие мутаций, публичный импорт и изоляцию.
   Проверять результат и структуру модели, а не только отсутствие исключения.
   Не объявлять процент покрытия без измерения; покрытие строк не доказывает контракт.
4. При необходимости выполнить из корня установленными инструментами:

   ```powershell
   npm test -- --runInBand --no-cache --coverage=false --runTestsByPath tests/<file>.spec.ts
   node node_modules/typescript/bin/tsc --noEmit
   ```

   Для общей регрессии убрать `--runTestsByPath` и путь. Для измерения покрытия
   использовать `npm run test:coverage -- --runInBand --no-cache --coverageDirectory <temp-path>`.
   Сборка `npm run build` пишет в `dist/`: если нужна проверка бандлов, выполнять
   её в изолированной временной копии. Не создавать и не править тесты в рабочей
   копии во время ревью. Записать команды, результаты и пропуски. Ошибку окружения
   отличать от дефекта кода. Успех Jest не заменяет strict-проверку TypeScript:
   в текущем `jest.config.js` для ts-jest задано `strict: false`.
5. Сохранить отчёт и кратко сообщить главные находки, ограничения и путь.

## Severity

Присваивать уровень по последствиям и воспроизводимости:

- **Critical** — потеря/искажение данных или серьёзная уязвимость на основном пути.
- **High** — неверный результат публичного API, нарушение совместимости,
  падение поддерживаемого сценария или ошибка экспортов/сборки.
- **Medium** — дефект отдельного граничного случая, существенный пробел проверки
  контракта тестами или подтверждённая проблема производительности.
- **Low** — локальная проблема сопровождения или документации с конкретным эффектом.

Не придумывать находки для заполнения отчёта; спорное предположение обозначать
как вопрос или ограничение. Известную незавершённую задачу поставки отделять от
обнаруженной регрессии.

## Отчёт

- Для одного явно выбранного активного change:
  `openspec/changes/<change>/reviews/YYYY-MM-DD-HHmm-<topic>-review.md`.
- Без change, для архивного или нескольких изменений:
  `review/YYYY-MM-DD-HHmm-<topic>-review.md`.
- Время — Europe/Moscow; topic — kebab-case, для этапа добавить `stage-N`.
  Создать каталог при необходимости, не перезаписывать существующие отчёты
  (при совпадении имени добавить числовой суффикс). Старые отчёты, включая
  одиночный `review.md` в change, не перемещать.
- Из `openspec/changes/<change>/reviews/` ссылки на код начинаются с
  `../../../../src/`, на тесты — `../../../../tests/`, на задачи — `../tasks.md`.
  Из `review/` — `../src/` и `../tests/`.

Структура отчёта:

```markdown
# Code Review — <topic>

**Date:** YYYY-MM-DD HH:mm (Europe/Moscow)
**Scope:** <files, diff/revision, change and stage if applicable>
**Revision:** <HEAD and working tree state>

## Summary
<Implementation assessment and main risks; explicitly state if there are no findings.>

## Validation
<Commands, results, limitations and environments not checked.>

## Findings
### 1. <title> [High]
- **Location:** <file link and lines>
- **Issue and evidence:** <input, expected/actual result, impact>
- **Recommendation:** <suggested correction without a ready-made patch>

## Test coverage
<Covered and uncovered scenarios, assertion quality and isolation.>

## Ranked findings
| Done | # | Severity | Finding | File |
| --- | --- | --- | --- | --- |
| [ ] | 1 | High | <title> | <link> |
```

В итоговой таблице перечислить все находки по убыванию severity с пустыми `[ ]`.
При отсутствии находок оставить строку `No findings` без фиктивного чекбокса.
