# BaSYS.FX Release Note Item

Добавить один нумерованный пункт о реализованном изменении библиотеки
`@basysteam/basys-fx`. Codex: `$bs-release-note-item`; Cursor: `/bs-release-note-item`.
Все пути относительны корню BaSYS.FX.

BaSYS.FX — публичный open-source проект. Текст релизного пункта писать на английском
для внешних пользователей библиотеки независимо от языка запроса и исходного
описания изменения. Ответ пользователю может быть на языке разговора.

## Файл выпуска

- Заметки находятся в `docs/relises/` — сохранить существующее написание каталога.
- Если пользователь указал версию или имя файла, выбрать соответствующий
  `docs/relises/<version>.md`. Не подменять явно выбранный файл другим.
- Без версии, в том числе для «текущего релиза», выбрать файл с наибольшей
  версией непосредственно в `docs/relises/`, без рекурсивного поиска.
  Сравнивать числовые части версии: `1.10.0` выше `1.9.0`, а не строки и не mtime.
  При наличии prerelease учитывать SemVer: основной выпуск выше prerelease
  той же версии. Если формат или выбор неоднозначен, уточнить.
- Не выбирать автоматически файлы из `published/` или других подкаталогов.
  Если пользователь явно указал опубликованный файл, убедиться, что он просит
  именно исправить его, прежде чем записывать.
- Не создавать файл выпуска без явного запроса. Если подходящего файла нет,
  подготовить текст пункта и запросить целевой выпуск. Версия в `package.json`
  служит контекстом и не заменяет правило выбора.
- Файл может быть пустым (как `docs/relises/1.1.0.md` на момент адаптации):
  в этом случае начать с `1.` без добавления заголовка или шаблона выпуска.

## Установить факты

Прочитать целевой файл и определить, что действительно реализовано. Использовать
контекст разговора, затем при необходимости `git status --short`, `git diff`,
`git diff --cached`, относящиеся новые файлы, `git log`/`git show`, реализацию
в `src/`, тесты в `tests/`, `README.md` и `docs/`.

OpenSpec proposal и незакрытые задачи показывают намерение, но не доказывают
готовность. Не включать запланированные функции, неподтверждённый выпуск сервера
и публикацию npm. Изменения tooling/скилов не выдавать за новую функцию библиотеки;
если запрос относится к ним, описать их реальный эффект для разработчика.

Проверить, не описано ли изменение существующим пунктом. Если описано полностью,
сообщить номер и не добавлять дубликат. Если нужно расширение существующего
пункта, предложить конкретный текст и уточнить намерение, когда изменение старого
пункта не было запрошено. Не править его автоматически.

## Формат и язык

- Один пункт, один абзац на английском, без внутренних переносов строк, заголовков,
  вложенных списков, emoji и блоков кода. Номер продолжает последнюю нумерацию
  релизных пунктов; в пустом файле — `1.`.
- Начать с результата для автора прикладного скрипта или потребителя библиотеки:
  что теперь можно сделать или какой неверный результат устранён.
- Для исправления кратко объяснить прежнее поведение. Для новой функции сразу
  перейти к назначению и использованию.
- Указать существенные значения, ограничения, область действия и совместимость,
  если они помогают использовать изменение. Размер абзаца соразмерен изменению.
- Имена публичных функций, типов, методов, параметров и пакета допустимы и полезны:
  `moment`, `beforeMoment`, `formatNumber`, `excludeOwn`, `@basysteam/basys-fx`.
  Оборачивать их и короткие примеры вызова в backticks. Это пользовательский
  интерфейс библиотеки. Внутренние имена файлов, классов реализации, коммиты,
  ветки и PR в пункт не включать.
- Не приписывать библиотеке контекст формы, выполнение SQL или серверные defaults.
  Зависимость от версии другого компонента указывать только по подтверждённым фактам.
- Сохранять терминологию публичной документации и существующих английских пунктов;
  русские термины из исходных материалов передавать по-английски. Ссылаться на другой
  пункт как `see item N` лишь при действительной связи.

Пример для реализованной возможности:

```markdown
1. Register queries now support boundaries based on a date or an operation moment. Use `beforeMoment`, `upToMoment`, `fromMoment` and `afterMoment` to set the start and end of a period, and `moment` to create a moment from an operation's date, metadata object and number. Date boundaries can target a specific date column through `column`, while `excludeOwn` controls whether the operation's own records are excluded. Boundaries are included in the query model and require server-side support to take effect.
```

Пример задаёт стиль, а не текст для автоматического добавления.

## Запись и результат

1. Непосредственно перед записью перечитать файл, проверить номер и дубликаты.
2. Вставить новый пункт после последнего релизного пункта с пустой строкой между
   ними. Если есть заключительный раздел `Deviations from the specification`,
   «Отклонения от ТЗ» или аналогичные
   служебные блоки, вставить перед ними; их списки не участвуют в нумерации релиза.
3. Сохранить существующий текст, нумерацию и стиль переводов строк; оставить
   завершающий перевод строки. Не менять версию, lock-файл и другие документы.
4. Проверить diff: добавлен только согласованный по объёму пункт в выбранный файл,
   ровно один абзац на английском, факты подтверждены кодом, прежние пункты не изменились.
   Сообщить путь, номер и добавленный текст.
