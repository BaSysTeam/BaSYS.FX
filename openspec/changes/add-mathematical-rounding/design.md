# Design

## Context

Мотивация и границы изменения описаны в [proposal.md](proposal.md), контракт — в [спецификации](specs/number-rounding/spec.md). Отдельного числового округления в библиотеке нет. Общие функции находятся в `src/common.ts` и реэкспортируются из `src/index.ts`. `formatNumber` использует `Math.abs(value).toFixed(decimals)` и возвращает строку; `parseNumber` отдельно преобразует строку с заменой `NaN` нулём.

В Construction вспомогательная `roundBy` используется через `round1/round2/round3/round6` и смешивает преобразование входа с округлением. Пользователь выбрал для библиотеки только числовой вход и отдельное преобразование. Проект собирается TypeScript/Rollup в ESM, UMD и IIFE, целевая версия ES6, доступные библиотеки ES2017; тесты — Jest/ts-jest. Изменений существующих спецификаций не требуется: основной каталог пока пуст.

Дизайн необходим для фиксации неоднозначности между двоичным значением `Number` и ожидаемым десятичным округлением, а также для выбора алгоритма без повторного округления промежуточных чисел.

## Goals / Non-Goals

**Goals:**

- Принять решение о половине на десятичных цифрах до единственного заключительного преобразования в `number`.
- Исключить промежуточное переполнение и зависимость от абсолютного допуска `Number.EPSILON`.
- Сохранить текущие форматы сборки и существующие функции без новых зависимостей и требований к среде.

**Non-Goals:**

- Восстановление точного исходного значения до преобразования в `Number` или до предыдущих арифметических операций.
- Гарантия точной десятичной арифметики после возврата результата; `0.1 + 0.2` остаётся обычной операцией JavaScript.
- Унификация округления и строкового представления: `formatNumber(1.005)` продолжит использовать прежний алгоритм и может отличаться от `round(1.005, 2)`.

## Decisions

### D1. Один публичный API и отдельная проверка входа

Разместить `round(value: number, digits: number = 0): number` рядом с общими функциями в `src/common.ts`. Существующий `export * from './common'` уже обеспечивает публичный экспорт: новый экспорт в `index.ts` нужен только если обнаружится реальная необходимость. JSDoc объясняет числовой результат и отсутствие конечных нулей. Никаких алиасов, прототипов и глобальной регистрации.

Проверять сначала тип `value`, затем тип и допустимость `digits`. Нечисловые аргументы дают `TypeError`; числовая недопустимая точность — `RangeError`. Только после этих проверок возвращать не конечное значение без изменения. Для всех нулей возвращать `+0`.

Альтернатива `Number(value) || 0` из примера скрывает ошибочный ввод; пользователь выбрал явное преобразование на стороне вызывающего кода. Сохранять `NaN` и бесконечности удобнее для композиции математических функций, чем вводить исключения для числовых результатов предыдущего расчёта.

### D2. Десятичный контракт по канонической записи

Для конечного ненулевого числа источником десятичных цифр служит `String(Math.abs(value))`. Половины округляются от нуля; решение принимается по модулю, знак применяется после округления. Это соответствует режиму `ROUND_HALF_UP` в decimal.js и даёт требуемый смысл отрицательным половинам.

Это осознанный десятичный контракт: `1.005` трактуется как десятичное `1.005`, хотя его двоичное представление немного отличается. Число `1.4999999999999998` остаётся ниже половины. Никакие искусственные допуски не приближают его к `1.5`.

Альтернатива округления точного двоичного значения формально корректна для `Number`, но не решает типичный прикладной пример `1.005 → 1.01`. Каноническая запись не восстанавливает потерянные цифры: литералы, ставшие одним и тем же `Number`, неразличимы.

### D3. Коэффициент и десятичный порядок без промежуточной арифметики Number

Внутренние шаги алгоритма:

1. Разобрать каноническую запись модуля, включая `e±n`, в строку целочисленного коэффициента и десятичный порядок: значение равно `coefficient × 10^exponent`. Удалить ведущие нули коэффициента; порядок учитывать с количеством дробных цифр.
2. Определить, сколько правых цифр коэффициента отбрасывается при данном `digits`. Если отбрасывать нечего, вернуть исходное число. Если разряд округления существенно старше числа, вернуть `+0`.
3. По первой отброшенной цифре выбрать сохранённый коэффициент: `0–4` оставляют его, `5–9` увеличивают на единицу. Перенос выполнять по строке цифр, включая случай всех девяток и пустой сохранённой части. Не преобразовывать коэффициент в `Number`: он может содержать больше безопасных целочисленных цифр.
4. Сформировать десятичную экспоненциальную строку округлённого результата и один раз преобразовать её в `Number`. Применить исходный знак и нормализовать ноль. Переполнение окончательного результата естественно даёт бесконечность.

Не строить огромные дополненные строки и не вычислять `10 ** digits`. Диапазон точности `[-308, 324]` покрывает десятичные порядки конечных и субнормальных `Number`; обработка опирается на короткую каноническую запись и ранние возвраты. Для `Number.MAX_VALUE` с точностью `2` число возвращается без масштабирования, а с точностью `-308` окончательный результат `2e308` становится `Infinity`.

Рассмотренные альтернативы:

- `Math.round(value * factor) / factor`: отличается на отрицательных половинах, ошибается на `1.005`, масштабирование может переполниться.
- Добавление `Number.EPSILON`: величина поправки зависит от масштаба задачи и не задаёт надёжного правила для всех чисел.
- `Number(value.toFixed(digits))`: округляет двоичный вход, не поддерживает отрицательную точность и не обеспечивает ожидаемое `1.005 → 1.01`.
- Сдвиг через экспоненциальные строки и `Math.round`: прост для обычных значений, но промежуточный `Number` может переполниться или округлиться до половины ещё до целевого шага.
- decimal.js/big.js: подходят для полноценной десятичной арифметики. Для одной операции над входным и выходным `number` новая зависимость не оправдана; при расширении задачи до точных денежных расчётов решение нужно пересмотреть.
- Целочисленная арифметика на `BigInt`: потребовала бы более новой среды, чем текущий ES6-контракт сборки.

### D4. Проверка контракта и документация

Создать `tests/round.spec.ts` с табличными ожидаемыми результатами из спецификации. Не вычислять эталоны через алгоритм реализации или `Math.round(value * factor)`. Проверять обе стороны половины и оба знака, перенос разряда, точности `1/2/3/6`, отрицательную точность, ошибки типов/диапазона, `Object.is` для нуля, субнормальные числа и окончательное переполнение. Отдельный тест импортирует функцию из `src/index.ts`.

Прогнать целевой набор, затем все тесты и `npm run build`; проверить наличие функции и декларации в создаваемых сборках. Сгенерированные файлы `dist` не включать в изменение. В `README.md` добавить краткие примеры и ссылку на `docs/round.md`; там описать типы, ошибки, диапазон точности, `NaN`/бесконечности, правила для половин и ограничения `Number`.

### D5. Источники общего поведения

- [ECMAScript: Math.round](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-math.round): стандартное разрешение половин к положительной бесконечности объясняет отличие предлагаемой функции.
- [ECMAScript: Number::toString](https://tc39.es/ecma262/multipage/ecmascript-data-types-and-values.html#sec-numeric-types-number-tostring): десятичное строковое представление и экспоненциальная форма.
- [decimal.js: режимы округления](https://mikemcl.github.io/decimal.js/#modes): `ROUND_HALF_UP` выбирает ближайшее значение и разрешает равенство расстояний от нуля. Используется как терминологический ориентир, библиотека в зависимости не добавляется.

## Risks / Trade-offs

- Ошибка переноса цифр или обработки экспоненты → контрактные примеры `9.995`, `1.25e-7`, `Number.MIN_VALUE` и большие числа с обоими знаками.
- Результат вновь представлен двоичным `Number` и может не быть точным десятичным кратным → явно описать финальное преобразование и ограничения; не обещать исправление последующих расчётов.
- Пользователь может ожидать форматированную строку или поведение `Math.round` на отрицательных половинах → показать короткие примеры обоих отличий в README и JSDoc.
- Десятичная обработка строк дороже одного вызова `Math.round` → короткие записи и ранний возврат; отдельный бенчмарк для этой утилиты не требуется без измеренной проблемы.
- Отличие от форматирования может удивить существующего потребителя → зафиксировать независимость API и не менять `formatNumber` в этой задаче.

## Migration Plan

Изменение добавляет новую функцию и не требует миграции потребителей. На этапе реализации подготовить исходники, тесты и документацию; версия и публикация выполняются отдельным релизным процессом. При последующем переносе прикладных обёрток отдельно проверить отрицательные половины и правила преобразования входа. Откат потребителя заключается в прекращении использования нового экспорта; существующие API не меняются.
